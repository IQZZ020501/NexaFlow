# MCP OAuth

HTTP MCP sources support a registered OAuth client configured by the source creator. Enter the provider's authorization, token and revocation endpoints, client ID, optional client secret and scopes. This mode uses PKCE S256 and resource indicators; it does not claim automatic issuer discovery or dynamic client registration. stdio keeps its existing isolated credential model.

Set the administrator-managed public site URL before connecting. Register `<site URL>/app/mcp/oauth/callback` with the provider. Redirect destinations never come from request Host headers. Only the creator can configure, authorize, inspect connection status or disconnect a source; workspace/global administrators have no implicit access. Explicitly granted tool users use the creator's connection, consistent with existing shared Bearer connections.

The callback binds a hashed, ten-minute state to the workspace, source, actor and credential generation. Verifiers, client secrets, access tokens and refresh tokens are encrypted with the persistent platform key. Responses never contain credentials. The callback page removes its query before exchanging the code. A callback is claimed before the token request and cannot replay an exchange whose outcome is unknown.

Token requests use bounded responses, timeouts, no redirects or environment proxies, and the MCP destination policy. Endpoints require HTTPS. Local HTTP testing is restricted to loopback with the deployment private-network override. Public-only destinations use DNS-pinned connections. OAuth is never a fallback from failed authorization to an unauthenticated MCP request.

Before an access token expires, a PostgreSQL row lock grants one worker a refresh lease. Other callers wait briefly and then report busy without dispatching a tool. A worker crash or uncertain refresh outcome requires reconnection rather than replaying a possibly rotated refresh token. Source generations fence late responses after disconnect or reconfiguration. MCP session reuse includes the credential fingerprint.

Disconnect immediately removes local credentials and preserves encrypted revocation intent in an independent outbox. The same intent survives source/account deletion. Celery Beat schedules bounded revocation batches with retry/backoff. A disconnected confidential client requires its secret to be entered again before reconnecting. Provider revocation availability remains an external dependency; disconnect already prevents local use while retries continue.

Owner-scoped routes live under `/api/v1/workspaces/{workspace_id}/mcp-servers/{server_id}/oauth`: GET status, PUT configuration and POST `authorize`, `callback`, `disconnect`. Creating an OAuth source does not discover tools until authorization completes. The callback attempts discovery; a discovery failure leaves the valid connection visible for a manual refresh.

Validation: `cd backend && uv run python -m tests.tools.oauth` uses a real local HTTP token/revocation endpoint and covers PKCE, replay, ownership, encryption, rotation, unknown refresh and a callback arriving after disconnect. `tests.tools.oauth_concurrency` requires an explicitly isolated PostgreSQL URL through `NEXAFLOW_TEST_DATABASE_URL`; ten concurrent requests produced one refresh, and an expired refresh lease did not replay. Migration `202611160004` upgraded, downgraded and upgraded successfully on isolated PostgreSQL 17. Frontend tests cover credential clearing, saved configuration and a single callback exchange under StrictMode. No production provider credentials or external accounts were used.
